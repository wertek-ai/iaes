# The reference scenarios, in Ignition

[`tags.json`](tags.json) is an **Ignition 8.3 tag export**. Import it and set one tag to `true`: the Gateway tells the
reference story -- a vibration reading, the diagnosis, the request to inspect, the closed work order, and one event type
IAES does not publish -- as five IAES events, chained by `correlation_id` and `source_event_id`, with the same
`content_hash` as every other implementation.

Reach for Ignition when the reading already lives in a SCADA/MES Gateway: the tag is there, and so are the screens where
plants track downtime and compute MTTR and MTBF from maintenance events.

## What is in the file

A folder `IAES_ReferenceStory` in the `default` tag provider:

| Tag | Type | What it is |
|---|---|---|
| `vibration_velocity` | Float8, memory, `4.2` | the reading (mm/s RMS). In production, point it at your sensor's tag. |
| `receiver_url` | String, memory, empty | where the batch is POSTed -- any IAES receiver. **Empty: nothing leaves the Gateway.** |
| `last_events` | String, memory | the five events of the last run, as a JSON list |
| `run` | Boolean, memory, `false` | set it to `true` to tell the story; its `valueChanged` script sets it back to `false` |

The script on `run` uses only the Python standard library (`json`, `hashlib`, `uuid`, `datetime`) and `system.*`, so it
runs on Ignition's Jython 2.7. It runs off the tag thread (`system.util.invokeAsynchronous`) and logs one line under the
logger `iaes.reference_story`. It is generated by [`build_tags.py`](build_tags.py), where it reads as ordinary Python;
`tests/test_reference_scenarios.py` checks that `tags.json` is what the builder writes.

## Steps

1. **Import** `tags.json` into the `default` provider: *Tags → Import* in the Gateway, or the Gateway API
   (`POST /data/api/v1/tags/import?provider=default&type=json&collisionPolicy=Overwrite`).
2. Optionally set **`receiver_url`** to your IAES receiver.
3. Set **`run`** to `true`. Read `last_events`, or what your receiver got.

## MTTR and MTBF from these events

The reference story is fixed (every implementation must emit the same five events), so it does not carry timing. In a
plant, `maintenance.completion` does:

- **MTTR** -- `data.actual_duration_seconds` is the time spent on the work order; the mean over completions is MTTR.
- **MTBF** -- `data.failure_confirmed` marks a completion that confirmed a failure; the time between those events'
  `timestamp`s, per asset, gives MTBF.

IAES has no field for the time the **asset was down** (as opposed to the time spent on the work order). If your MTBF needs
it, that is a gap in the standard, and the way to close it is an RFC (`GOVERNANCE.md`).

## How it is checked

- **On every commit** -- [`run.py`](run.py) reads the `run` tag's script out of `tags.json`, unchanged, and executes it on
  CPython as the body of `valueChanged(...)`, with a stand-in for `system.*` (tag reads and writes from the file's
  defaults, a recording logger, `invokeAsynchronous` run at once; a POST fails the run, because `receiver_url` is empty).
  The test compares the five events with `scenarios/fixture.json` and their `content_hash` with the other
  implementations'.
- **What that does not prove** -- that Jython 2.7 produces the same bytes (the hash depends on `json.dumps` and float
  formatting), that the tag types import, and that the Gateway fires the script. Those need a real Gateway; see below.

## Contract

```
CONTRACT      iaes
INPUT         the `vibration_velocity` tag (4.2 mm/s RMS as shipped) and a write of `true` to `run`
OUTPUT        five IAES 2.0 events (asset.measurement, asset.health, maintenance.work_order_intent,
              maintenance.completion, acme.press_stroke) as one JSON list in `last_events`, and POSTed as one batch to
              `receiver_url` when it is set
PRESERVE      one correlation_id for the chain; source_event_id pointing at the event each one follows; content_hash
              as every other implementation computes it; the custom type written by hand, without a hash
DO NOT INFER  · that your provider is called `default`
              · that a value read with bad quality is usable: the run fails and logs instead
              · Ignition versions other than 8.3.x
IDEMPOTENCY   every run emits new event ids and a new correlation_id
ACCEPTANCE    python scenarios/ignition/run.py, and tests/test_reference_scenarios.py on every commit
STATUS        CPython with a stand-in for system.* on every commit. Real Gateway: see the line below.
```
